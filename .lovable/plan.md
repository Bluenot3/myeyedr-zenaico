# Bulk Intake + Requisitions + Candidate Command Center

Extend the current recruiting app (candidates, positions, pipeline) with multi-resume upload, a proper requisition layer, master-person candidate history, and a premium editable table — reusing existing components, tokens, hooks, and RLS patterns.

## 1. Data model (migrations)

Treat the existing `positions` table AS the requisition (extend, don't duplicate). Add durable history + applications join tables.

**Extend `positions`** (requisition fields):
- `req_code` text (auto human ID like `REQ-0007`, generated by a sequence/trigger), `hiring_manager` text, `date_opened` (default now — `created_at` already covers this so reuse it). Headcount = existing `openings`, status/priority already exist.

**Extend `candidates`** (richer parsed data, master record):
- `address` text, `current_employer` text, `work_history` jsonb, `education` jsonb, `certifications` jsonb, `resume_summary` text, `resume_text` text (raw parsed text), `parse_confidence` numeric, `screening_status` text (default `not_started`), `interview_status` text (default `not_started`). Skills already map to `tags`/`best_fit_roles`.

**New `candidate_requisitions`** (applications — a candidate ↔ requisition link, keeps full assignment history):
- `id`, `candidate_id` (FK), `position_id` (FK, nullable), `location_id` (FK, nullable), `stage`, `status` (active/rejected/withdrawn/hired), `source`, `is_primary` bool, `notes`, `created_by`, `created_at`, `updated_at`. The candidate keeps its current `position_id`/`location_id` as the primary pointer; this table records every job/store/role they've ever been tied to.

**New `candidate_events`** (durable timeline):
- `id`, `candidate_id` (FK), `event_type` (assignment / stage_change / screening / interview / note / rejection / withdrawal / reconsideration / requisition_add), `title`, `detail` jsonb, `requisition_id` (nullable), `location_id` (nullable), `actor` text, `created_at`.

**Tie screenings/interviews to requisitions:** add nullable `requisition_id` (position_id-style) reference is already present on `interview_events` and `candidate_evaluations` via `position_id`; add `location_id` where missing and an explicit `requisition_id` column so each screening/interview clearly belongs to a specific req. Keep them visible regardless of the candidate's current role.

**RLS + GRANTs (mandatory, per existing pattern):** every new table gets `GRANT SELECT, INSERT, UPDATE, DELETE ... TO authenticated`, `GRANT ALL ... TO service_role`, `ENABLE ROW LEVEL SECURITY`, and policies using the existing `can_access_candidate(auth.uid(), candidate_id)` / `can_access_location(...)` helpers so no access control is weakened. A `req_code` sequence + `BEFORE INSERT` trigger generates the requisition code. `updated_at` triggers reuse `public.update_updated_at_column()`.

## 2. Resume parsing upgrade (`supabase/functions/parse-resume`)

Extend the existing edge function's extraction schema to also return: `address`, `current_employer`, `job_titles`, `work_history` (array of {employer, title, dates}), `education` (array), `certifications` (array), `resume_summary`, `raw_text`, and a `confidence` score, alongside the current fields. Keep the existing robust multi-path JSON extraction untouched.

- **File formats:** PDF and images continue to go to the model as a data URL (works today). Add **DOCX/DOC** support by extracting text in the browser with `mammoth` (docx) before calling the function, sending the text as a `text` message part. Unsupported/failed files surface a clear per-file error but never block the batch.

## 3. Bulk upload flow (new `BulkResumeUpload.tsx`)

Full-screen intake surface (reuses the full-screen dialog pattern already in `AddCandidateDialog`):
- **Default assignment bar** (applied to all, editable per candidate later): Location, Position/requisition, Source, Tags.
- **Multi-file dropzone** (accept `.pdf,.doc,.docx,.png,.jpg,.webp`, many at once).
- **Per-file status list**: queued → uploading → parsing → parsed/failed, with progress and inline error text. Each file uploads the original to the `candidate-documents` bucket (preserved + linked) and parses concurrently (small concurrency limit).
- **Duplicate detection**: before creating, match against existing candidates by exact email, normalized phone, and fuzzy full-name; flag likely duplicates in the review grid with a "merge into existing / create new / skip" choice (default = attach as a new application to the existing master record, not a new person).
- **Review grid**: parsed candidates shown as editable rows before commit; user can fix any field, override the per-row assignment, then "Add N to pipeline". Each commit creates/updates the master candidate, a `candidate_requisitions` row, and an initial `candidate_events` entry.

## 4. Candidate command-center table (new `CandidateTable.tsx`)

Add a **"Table"** view mode alongside the existing Board/List toggle in `PipelineBoard` (and surface the Bulk Upload button there):
- Polished rows with sticky header, status badges (reuse `StageBadge`, tokens), avatars/initials.
- **Editable / dropdown cells:** Location, Position/requisition, Pipeline stage, Screening status, Interview status, Source — inline-saved via existing `useUpdateCandidate` + new application hooks.
- **Search + filters:** location, position, requisition, stage, source, date uploaded, screening/interview status.
- **Row actions menu:** view profile, edit details, assign/reassign requisition, add screening note, add interview note, move stage, archive/reject, open resume.
- Responsive: collapses to a dense card layout on mobile, matching current design language (no new visual style).

## 5. Candidate profile history

In `CandidateProfile.tsx` add an **Activity / History** section (new tab or panel) rendering the `candidate_events` timeline plus the list of all `candidate_requisitions` (past & present, with which store/role/req and outcome), and make existing screenings/interviews show their linked requisition. The profile stays one master record with multiple applications.

## 6. Hooks (`src/hooks/useRecruiting.ts`)

Add typed interfaces + queries/mutations: `useCandidateRequisitions`, `useCreateApplication`, `useReassignRequisition`, `useCandidateEvents`, `useLogEvent`, and extend `Candidate`/`Position` types with the new fields. Reuse existing query-invalidation and toast patterns.

Verify end-to-end with Playwright against the live preview: bulk upload of several resumes → parsed grid → commit → candidates appear in the table with correct requisition/location → open profile shows history → reassign requisition preserves prior application → reject archives with flag. Confirm no regressions to the existing Add Candidate, pipeline board, evaluations, or onboarding flows.

## Notes / trade-offs
- `positions` is reused as the requisition entity to avoid a fragmented parallel table; a `req_code` gives it a real requisition ID. If you'd prefer a fully separate `requisitions` table, say so and I'll split it.
- DOCX parsing relies on client-side text extraction (`mammoth`); scanned-image PDFs still rely on the model's OCR as today.
